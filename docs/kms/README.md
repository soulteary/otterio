# KMS guide

OtterIO uses a key management service (KMS) for SSE-S3 object encryption. Each
object has its own encryption key, protected with a data key generated by the
configured KMS. The encrypted data key and key identity are stored in object
metadata; the master key remains with the KMS. See the
[encryption overview](../security/README.md) for the key hierarchy and SSE-C.

This guide describes the configuration in [cmd/crypto/config.go](../../cmd/crypto/config.go)
and the mTLS KES client in [cmd/crypto/kes.go](../../cmd/crypto/kes.go). KES is an
external service, not an OtterIO project. The original
[MinIO KES repository](https://github.com/minio/kes) is archived and marked
deprecated. Its [configuration documentation](https://github.com/minio/kes/wiki/Configuration)
is a historical reference, not an OtterIO endorsement or a guarantee that a new
KES/KMS product is compatible with this client.

## Prepare your own KES and key store

Use a service and key store under your control. Before starting OtterIO:

1. Select and verify the exact KES implementation/version and its backing key
   store. This client uses the `/v1/key/generate/<name>` and
   `/v1/key/decrypt/<name>` APIs with encryption context. Administrative key
   creation uses `/v1/key/create/<name>`.
2. Configure the KES server's HTTPS certificate, a dedicated OtterIO client
   certificate/private key, and the policy for that client identity. Give it
   access to generate and decrypt data keys for the intended master key.
   Provision that master key with your KES operator tools before uploading data;
   configuring its name in OtterIO does not create it. Grant key-creation access
   only if your administration workflow needs it.
3. Ensure the KES server certificate covers the hostname in the endpoint URL.
   Provide the issuing CA certificate when it is not already trusted by OtterIO.
   The client certificate/key must be readable by the OtterIO service account.
4. Establish backup, recovery and access controls for the backing key store.
   Retain keys needed to read existing objects, including after changing the
   default key. Losing a required key makes those objects unreadable.

[kes-config.toml](kes-config.toml) is a legacy example, not a ready-to-run
configuration for current KES releases. It contains an example client identity,
relative certificate paths, empty Vault AppRole credentials and `otterio-*`
policy paths. Use the configuration format and identity procedure required by
your selected service/version; replace those values rather than applying the
file unchanged. Its Vault section configures the KES backing store, not
OtterIO's direct Vault adapter.

No shared playground identity or public KES instance is required by this guide.
Do not use a publicly distributed private key for your own encrypted data.

## Configure and start OtterIO

Install OtterIO using the [project instructions](../../README.md#installation).
Configure and save your own root credentials as described in
[Quick Start](../../README.md#quick-start). Replace the example KES hostname,
file paths and master-key name below with the values provisioned above:

```sh
export OTTERIO_KMS_KES_ENDPOINT=https://kes.example.net:7373
export OTTERIO_KMS_KES_KEY_FILE=/etc/otterio/kms/client.key
export OTTERIO_KMS_KES_CERT_FILE=/etc/otterio/kms/client.crt
export OTTERIO_KMS_KES_CA_PATH=/etc/otterio/kms/ca.crt
export OTTERIO_KMS_KES_KEY_NAME=otterio-data

test -r "$OTTERIO_KMS_KES_KEY_FILE"
test -r "$OTTERIO_KMS_KES_CERT_FILE"
test -r "$OTTERIO_KMS_KES_CA_PATH"
: "${OTTERIO_ROOT_USER:?Restore your saved root username}"
: "${OTTERIO_ROOT_PASSWORD:?Restore your saved root password}"
export OTTERIO_ROOT_USER OTTERIO_ROOT_PASSWORD

mkdir -p "$HOME/otterio-kms-data"
otterio server --address 127.0.0.1:9000 \
  --console-address 127.0.0.1:9001 "$HOME/otterio-kms-data"
```

This starts a local OtterIO server using HTTPS/mTLS to KES. The local S3 and
console listeners use HTTP; use the [OtterIO TLS guide](../tls/README.md) for an
HTTPS deployment. The KES CA setting trusts the KES server and does not configure
TLS on OtterIO's listeners. A CA path may be a PEM file or a directory of PEM
certificates. Multiple KES endpoints may be comma-separated and must reach the
same required keys. Configure KMS access on every node of a distributed server.
For containers, mount the client certificate, private key and CA at the paths
visible inside the container; follow the [container credential guide](../../README_DOCKER_SECURITY.md).

Use one KMS configuration at a time. A static `OTTERIO_KMS_MASTER_KEY` or legacy
`OTTERIO_SSE_MASTER_KEY` conflicts with configured KES/Vault; direct Vault and KES
also conflict. Existing installations should review their environment and
persisted KMS configuration before switching. The direct Vault adapter is a
legacy path, disabled unless explicitly opted in; it is separate from using
Vault behind KES. This guide does not enable that adapter or change its policy.

## Enable bucket default encryption

Use the companion [OC client](https://github.com/soulteary/oc) and an identity
authorized for the target bucket's encryption configuration. In a second shell,
connect to the local server, enter its configured credentials when prompted,
and choose a new bucket name:

```sh
oc alias set kms-local http://127.0.0.1:9000 \
  --api s3v4 --path on --admin-url http://127.0.0.1:9001
oc mb kms-local/kms-check
oc encrypt set sse-s3 kms-local/kms-check
oc encrypt info kms-local/kms-check
```

Bucket encryption uses the S3 endpoint; OC administration uses the separate
admin endpoint in this example. OtterIO's bucket-default configuration currently
accepts one `AES256` / SSE-S3 rule, as enforced by
[validateBucketSSEConfig](../../cmd/bucket-encryption.go). A client advertising
an `sse-kms` bucket-setting command does not establish that this server accepts
that configuration. Enabling a default affects new writes; it does not rewrite
existing objects. Explicit SSE-C requests use the supplied customer key instead
of the KMS and require HTTPS.

The server also retains `OTTERIO_KMS_AUTO_ENCRYPTION=on` for a server-wide
SSE-S3 default. It requires a valid KMS; startup rejects that option without one.
Prefer explicit bucket configuration when individual buckets need different
defaults. Verify gateway behavior separately rather than assuming the server
mode example applies to every backend.

## Verify encryption and recovery

After configuring KMS and the bucket default:

```sh
printf 'OtterIO KMS check\n' > kms-check.txt
oc cp kms-check.txt kms-local/kms-check/check.txt
oc stat kms-local/kms-check/check.txt
oc cp kms-local/kms-check/check.txt kms-check-downloaded.txt
cmp kms-check.txt kms-check-downloaded.txt
```

Check the object's encryption metadata for
`X-Amz-Server-Side-Encryption: AES256`, and confirm that the downloaded bytes
match. A successful bucket configuration alone does not prove that the service
can generate or decrypt data keys. In staging, also restart OtterIO with the
same KMS/key store, read the existing object, and validate key-store recovery,
multipart uploads and copies required by your workload. Key rotation does not
make old keys disposable while objects still reference them.

The environment names, API paths and bucket-default behavior above were checked
against this repository's source. The OC command syntax was checked against the
companion client. This documentation update did not provision a KES service or
run a live KES-backed encryption/recovery test; validate your selected service,
certificates, policy and backing store before deployment.
