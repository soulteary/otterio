# OtterIO 新版本：补强存储安全边界，完善容器部署与发布

> 发布准备稿，整理日期：2026-10-05。本文不是发布成功证明。
> 对比基线：`RELEASE.2026-10-04T09-24-10Z`。
> 内容核对至 `c5ecf86801011576468737d2a1d349be7a5e3999`（已合并 #18–#27）。
> 在 #25 初稿上补齐 #26 存储安全和 #27 清单修复；详见[提交核对与验收清单](2026-10-05-release-review.md)。
> 发布前按[发布指南](../releasing.md)生成新标签，确认产物与 `latest` 状态，
> 再将这段准备说明替换为实际版本号、Release 链接和验证结果。

这次 OtterIO 更新的重点，不是增加一长串新功能，而是继续把对象存储最基础的事情做好：
请求处理更可靠，容器启动少一些隐式行为，构建使用的源码和用户下载到的产物能够对应起来。

在上一版安全更新的基础上，这次准备发布的内容主要围绕内部存储边界、容器部署、
流式响应、依赖维护和发布链路展开。上一份准备稿之后，又合并了两项重要修正，
这次一起纳入，避免只更新公告、却漏掉真正需要交付的修复。

## 内部存储，也不能无条件信任另一台节点

这次新增的 [#26](https://github.com/soulteary/otterio/pull/26) 针对内部存储层补上了多处校验：
路径在规范化前检查，元数据请求体中的路径也要检查；重命名双方、批量操作的所有条目
在实际修改文件前完成预检；删除边界按路径段判断，而不是只比较字符串前缀。

纠删码参数、分片大小和 V1/V2 元数据也增加了合法性检查，避免异常长度、数组不一致、
除零、溢出或未知 bitrot 算法导致错误。MessagePack 在分配解码集合之前检查声明大小、
层级和总值数量，流式校验使用固定 32 KiB 缓冲，不跟随对端声明的分片大小分配。

这里需要明确威胁边界：分布式内部存储 REST 使用节点/root JWT 认证，
不是匿名 S3 请求或普通受限 S3 密钥就能调用。但对端有内部身份，也不意味着它提供的
路径、元数据和长度可以不检查；单节点部署同样不能替代对共享存储代码的修正。

新限制针对内部缓冲 RPC：单次缓冲操作和元数据请求体最多 **64 MiB**，
单批版本删除最多 **1,000** 项，**不是把 S3 对象大小限制为 64 MiB**。
大对象仍走流式路径；自定义内部客户端应调整过大的缓冲操作和批次。

升级时应覆盖所有分布式节点，并提前备份元数据。不合法的历史元数据会被拒绝为损坏，
不会自动改写或删除；请调查并使用已知良好的副本恢复，而不是关闭验证。
这些检查是词法路径边界，不是符号链接或并发文件系统操作的沙箱，
单请求限额也不是全局并发内存预算。实现和限制见[存储加固说明](../security/sn-2026-002-storage-hardening.md)。
SN-2026-002 相关工作是 OtterIO 的独立实现，不代表其他项目的全部公告内容原样适用，
也不包含 OIDC 修改。

## 容器启动，不再默默接受默认凭据

这是容器用户升级前需要检查的一项行为变化。

容器里的 `server` 和 `gateway` 命令现在要求显式设置非默认凭据。
过去没有配置用户名和密码也能启动的命令，新版本会直接停止并给出提示。
现有的现代凭据变量和旧版变量仍然支持，但不能混用两套配置的半对值。

密钥文件也改为逐项独立读取：用户名放在环境变量中、密码放在挂载文件里，可以正常组合。
显式配置的文件不存在、不可读、不是普通文件或为空时会报错；同一项同时出现环境值
与已有密钥文件时，也不会再用隐式优先级掩盖配置冲突。错误信息不输出密钥内容。

同时新增了可选择使用的安全 Compose 配置，包含非 root 用户、只读根文件系统、
受限临时目录、回环端口、移除 capabilities 和禁止提权。
这里没有直接改变镜像默认 UID，也不会自动修改已有数据目录归属。
采用非 root 配置前，应先检查数据和密钥文件的权限，不能把递归修改生产目录权限
当作通用迁移步骤。裸机二进制不受这项容器入口策略改变的影响。

具体配置见[容器迁移说明](../../README_DOCKER_SECURITY.md)。
默认凭据的例外开关只用于隔离的本地演示，不是生产环境的升级办法。

## 构建当前源码，而不是另一个 main

此前的 Docker 构建路径会另外获取远程 `main`，本地修改和最终镜像可能不是同一份内容。
这次调整后，镜像直接从提供的构建上下文编译，包括仓库中提交的浏览器生产资源。

源码身份信息允许显式传入并进行校验；无法确定提交时就明确标记为 `unknown`，
不伪造一个看似可靠的版本标识。

这解决的是“到底构建了哪份源码”，不等于已经实现逐字节可复现构建。
构建输入一致、产物校验和一致、镜像有签名，是不同层面的事情。
对应实现见 [#20](https://github.com/soulteary/otterio/pull/20)。

## 流式响应，明确跨协程的状态边界

在流式请求处理里，响应头和状态码一旦提交，就不应该再被另一个协程看到的可变状态覆盖。

这次为流式响应增加了不可变快照，明确区分提交响应头之前的异常，以及已经开始输出
之后的流错误；同时覆盖后续响应头修改、部分输出后异常和消费者关闭等情况。
这些改动的目标是修复具体的并发行为，而不是宣传一个未经测量的吞吐提升。
对应实现与回归范围见 [#19](https://github.com/soulteary/otterio/pull/19)。

## 发布完成，再提升 latest

发布流程也做了一次梳理：源码、二进制、镜像和发布说明固定到同一标签提交，
并且必须通过该提交在 `main` 上的规定 CI 检查。PR 里的绿色状态不能代替这个检查。

流程先构建二进制，再推送固定版本镜像。镜像推送后，使用实际摘要运行 Linux amd64
上的启动及 S3 创建、上传、下载、删除验证；这不等于已经在所有镜像架构上完成运行测试。

随后把附件上传为 GitHub Release 草稿，再下载并逐个比对，验证通过才发布。
新增的 `release-manifest.json` 记录源码提交和镜像摘要，便于核对版本身份。
最后通过串行的晋升流程验证摘要与版本顺序，再更新镜像 `latest` 和 GitHub 的最新版本标记。
较旧任务不能通过这条流程把 `latest` 拉回旧版本。

之前的发布尝试还暴露出一个具体问题：镜像仓库名中包含被配置为 secret 的用户名时，
GitHub Actions 会省略相关 job 输出。构建与镜像测试可以成功，下游却拿到空仓库名，
直到晋升校验才发现清单无效。

[#27](https://github.com/soulteary/otterio/pull/27) 已将仓库名改为在发布任务内确定，
跨任务只传真实构建摘要和明确的 Docker Hub 发布选择，不假设 Docker Hub 与 GitHub
用户名相同。清单生成与晋升共用校验，缺少必要信息就停止，不再把错误元数据上传为正式附件。

这仍不是跨平台的原子事务：固定版本镜像可能先于 Release 存在，晋升失败也可能造成
别名短暂不一致。**只有身份清单有效、固定标签和摘要一致时**，才适合单独重跑晋升。
清单损坏、缺失或与源码/镜像不匹配时，重跑不会自动修复；应修复后用新标签完整发布，
而不是覆盖正式附件、移动旧标签或放宽校验。旧标签也不会包含后来合并的存储加固。
身份清单不是签名或供应链证明。
对应实现见 [#22](https://github.com/soulteary/otterio/pull/22) 和 #27，恢复方法见[发布指南](../releasing.md)。

## 升级依赖，也更新真正交付的前端资源

源码构建的最低 Go 版本提升到 **1.27.1**，同时更新 Fiber、fasthttp、etcd、S3 SDK
以及相关依赖。浏览器开发环境统一到 **Node 24.21.0 / Bun 1.4.2**，同步更新 React、
路由、Babel、测试和打包工具。

这次不只是修改依赖声明：生成的 Go 代码、浏览器锁文件以及嵌入服务端的生产资源
都进行了同步更新。完整版本变化和兼容性边界见[依赖升级记录](../development/dependency-upgrade-20261004.md)。
直接运行二进制或镜像的用户，不需要因此在宿主机安装这些开发工具。

CI 则改为从当前检出的 `go.mod` 读取 Go 工具链，调整编译缓存，去掉竞态测试前
无用的普通构建，并保留完整、实际执行的竞态检查。诊断结果用于判断耗时来源，
不通过缩减测试或复用成功测试结果来制造“提速”。目前不对外宣称数值化性能收益。
对应实现见 [#23](https://github.com/soulteary/otterio/pull/23) 和 [#24](https://github.com/soulteary/otterio/pull/24)。

## 安全修复与社区贡献，继续保留清晰记录

上一正式版本 `RELEASE.2026-10-04T09-24-10Z` 已经包含 SigV4 请求头签名覆盖修复、
Windows 启动修复和动态超时测试确定性改进。这些不是这次才出现的改动，
但仍在使用六月版本的用户需要一起关注。

SigV4 修复会拒绝未被签名覆盖的 S3/OtterIO 操作请求头；合法签名的复制仍然支持。
自定义客户端应在签名时提供相关请求头，不应签完再追加，更不能通过关闭校验绕过拒绝。
本项目不借用其他产品的 CVE 编号，也不把一次修复描述为解决了全部历史安全问题。

特别感谢 **Oren Yomtov of Act Security** 对 SigV4 问题提供安全反馈、分析和复现用例。

## 升级建议

先备份数据和配置，并验证恢复；再检查凭据、文件挂载和目录权限，在测试环境完成
正常上传、下载、删除、分片上传和合法签名复制验证，涉及 Windows 的部署还应检查启动行为。
分布式环境还应核对每个节点的实际版本、已有对象读取、修复/复制和大对象流式读写。
滚动升级期间仍有未加固节点；出现历史元数据损坏错误时，先调查，不要跳过校验。

选择实际发布的新版本标签或已经核对的镜像摘要，不依赖本地缓存的 `latest`。
二进制核对 SHA-256，镜像与 `release-manifest.json` 的身份记录对应。
相关改动没有引入存储格式迁移，但这并不是无条件降级保证。

对一个存储服务来说，能启动只是第一步。把配置错误提前暴露，让构建、验证和交付
能够互相核对，才是这次更新希望继续做扎实的事情。
